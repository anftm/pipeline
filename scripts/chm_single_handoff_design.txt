Interrupted single-CHM handoff: design notes, NOT an execution procedure
=======================================================================

Status and scope
----------------
The 2026-11-03 CHM conversion wrote a new chapter bundle and canonical index;
the sidecar handoff failed when the HF Reader endpoint returned 503. The old
route still serves the book. The new bundle has an active processing pin.
Fifty-one earlier ebook processing pins are also active. Do not rerun the CHM
workflow, invoke its normal sidecar apply step, release any pin, or run GC.

The accompanying shadow modules are pure in-memory exploratory models. They
have no CLI, storage adapter, deployment, or activation path. Even a successful
observation explicitly reports recovery_authorized=false and
external_writers_fenced=false. They are not production plans, executable
recovery protocols, or substitutes for consumer verification. The existing
read-only preflight workflow runs only their offline tests, never the modules
as production commands.

Why the ordinary helpers cannot be reused
-----------------------------------------
The normal handoff considers all indexed processing records and would change
51 earlier pins in addition to the CHM pin. publish_catalog() can compact
acknowledged catalog history and emit retirement hints. v3 publication writes
several objects, an active pointer, and consumer projections. Those steps are
not one transaction and have independent external writers. Per-key ETags do
not prove exclusion, prevent an ABA change, or make those writes atomic. The
store's observed control objects had no VersionId at the last read.

The offline models do not perform v3 or consumer state transitions. The base
catalog model preserves historical entries and the prior current generation's
references, but does not construct its snapshot, establish a complete graph,
or decide whether that candidate is publishable. The projection-only model
constructs hypothetical in-memory v3 identities and tests synthetic fixtures;
it never fetches consumer responses or adapts the document reset receipt.
Input hashes and listings are observations, not signatures or trusted evidence.
The production preflight is read-only; its central lock does not fence external
writers.

An additional v3/document-reset incompatibility
----------------------------------------------
The live parent v3 catalog includes document_reset and the existing withdrawn
document-reset receipt binds that exact generation and base snapshot. The
ordinary unify() candidate omits document_reset when it creates a generation.
Even if a hypothetical replacement preserves that field, the historical receipt
still names the old generation and snapshot. reader_gc_documents.preflight()
requires all three identities to match the current catalog, so it must reject
such a replacement until a separately reviewed compatibility protocol exists.
Do not bypass that preflight, edit the receipt, or run document GC. CHM-only
route acceptance cannot by itself establish document-retirement compatibility.

The converse also fails: merely changing the receipt to name a hypothetical new
generation and base does not prove a safe CHM handoff. The current document GC
preflight intentionally permits each deployed document-withdrawn projection to
equal either the canonical sidecar or its pinned baseline. In a synthetic test
where those differ, one consumer with the old route and another with the new
route pass that narrow projection condition. Document withdrawal checks and CHM
two-consumer acceptance answer different questions; neither replaces the other.
The test fabricates a receipt in memory solely to show this counterexample; it
does not validate a migration or recommend updating any real receipt. Multiple
remaining GC preflight checks, fences and the 52 processing pins still apply.

An unchanged apply=true unify is not necessarily a no-op either: the central
workflow currently sets changed=true unconditionally, then can publish a Pages
projection, acknowledge consumers, and compact the base catalog. A read-only
unify apply=false result therefore does not authorize an apply=true retry.

Requirements to prove before any separately reviewed implementation
---------------------------------------------------------------------
1. Independently establish a current writer inventory and durable exclusion
   covering central, external, manual, credential and deployment writers.
   Disable/drain/recheck all relevant writers for the complete interval;
   treat an unavailable API, identity mismatch, recreated repository, expired
   fence, unsupported conditional API or unknown job as a hard stop. The old
   maintenance journal and deleted repositories do not prove this exclusion.
2. Re-read the original run/attempt and exact pinned CHM, processing, index,
   sidecar, legacy catalog, v3 pointer, source and bundle; verify their bytes,
   ETags and identities. Verify all 51 old processing records, unique owners,
   resources, and the new CHM pin without releasing any of the 52. Independently
   establish all source/index dependencies and both full consumer projections.
   Any changed object, incomplete listing or unreachable endpoint stops work.
3. Define a durable, authenticated intent with an immutable transaction ID,
   exact expected bytes and strong conditional identities for every controlled
   object, all prior and proposed states, dependencies, allowed actions and a
   complete preservation inventory. Create it conditionally and verify it;
   make recovery possible after an interruption before relying on it. Never
   trust a self-hashed plan as authorization.
4. Independently review the full base catalog/reference graph and deterministic
   snapshots. Keep every prior generation, every parent reference, bookmarks,
   source objects, chapter bundles and all processing pins. No catalog history
   compaction, processing handoff, retirement hint or deletion is implied.
5. Specify each candidate immutable object and each mutable single-key CAS,
   including exact serialization, expected original and result ETags/bytes,
   pre/post-read verification, overlapping writers, ABA and uncertain outcomes.
   Treat missing/mixed/foreign objects as stops; never blindly repeat a timed-out
   call, dispatch, or rebase. Reconciliation must first establish the exact
   durable state and current fence, and must not turn divergence into overwrite.
6. Specify how old and new v3 pointers, snapshots and promotion records are
   created and recovered; address parent changes and partial base/catalog/v3
   sequences. Ensure no existing producer or consumer can observe an unsafe
   combination. If this cannot be proved, do not write even the first object.
7. Define independent full HF and Pages acceptance against the exact resulting
   generation and every route, including the target and unaffected entries.
   Handle outages, stale deploys, partial acknowledgments and changed Space
   code without inferring success. Preserve all 52 pins even after acceptance
   until any release has its own separate reviewed authorization.
8. Test each conditional-write conflict and interruption before/after every
   phase, lost responses, replay, external races, stale projections, pin and
   history drift, corrupt or truncated inventories and repeated recovery.
   Use independent tests/review and real API semantics; this shadow's mock CAS
   only illustrates failure cases and does not demonstrate those semantics.

GC and credential isolation must be reviewed separately. Nothing here permits
restoration of old remote OCR, expanded scans or limits, extra backup, routing
withdrawal, source deletion, processing release, retirement hints, or GC.
